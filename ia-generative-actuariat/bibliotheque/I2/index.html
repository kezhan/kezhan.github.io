I2. Vectorisation d’un Monte Carlo non-vie naïf

Cette fiche illustre la démarche E sur la performance. Ce que vous apprenez n’est pas le Monte Carlo non-vie, mais comment passer de boucles for Python à du NumPy vectorisé, comment mesurer le gain honnêtement, et comment vérifier que la version rapide simule toujours le même modèle (contrôle par les moments théoriques).

TipDémarche illustrée : E, industrialiser un calcul (performance)

La démarche se pratique en direct dans l’atelier de la demi-journée « Automatisation et industrialisation » du support.

Le contexte métier

Beaucoup de calculs actuariels reposent sur du Monte Carlo : simulation de la charge annuelle, projection de portefeuilles, stress-tests réglementaires. Écrite avec des boucles for Python imbriquées, une simulation passe son temps dans l’interpréteur ; vectorisée en NumPy, elle confie les mêmes tirages à du code compilé. Sur l’exemple de cette fiche, la version vectorisée va des dizaines de fois plus vite, et c’est ce qui rend une étude de sensibilité faisable ou non.

Ce cas illustre la transformation. On part d’un script naïf typique (celui qu’écrit un actuaire qui débute en Python), on demande à Claude de le vectoriser, on mesure le gain sur ce poste, et on vérifie que les deux versions simulent bien la même loi.

Ce cas sert de démonstration express dans l’atelier du deuxième après-midi (« Automatisation et industrialisation ») : sur un poste qui ne calcule rien d’autre, la version naïve tourne en quelques secondes (de 3 à 5 sur le poste de rédaction peu chargé), assez peu pour être lancée devant la salle.

Donnée d’entrée

On simule la charge annuelle d’un portefeuille auto : 5 000 polices, nombre de sinistres par police de loi de Poisson de paramètre \(\lambda = 0{,}1\) par an, coût d’un sinistre log-normal (\(\mu = 7\), \(\sigma = 1{,}2\)). C’est une simulation paramétrique : les tirages viennent d’une loi posée, pas d’un rééchantillonnage de données observées (ce que serait un bootstrap).

Le modèle a l’avantage d’avoir des moments connus. La charge totale \(S\) est une Poisson composée de paramètre \(N\lambda\), donc

\[ \mathbb{E}[S] = N\lambda\, e^{\mu + \sigma^2/2}, \qquad \operatorname{Var}[S] = N\lambda\, e^{2\mu + 2\sigma^2}. \]

Ces deux valeurs serviront de juge entre les versions.

Deux tailles de simulation. La version naïve tourne sur 200 simulations, pour rester à quelques secondes (la démonstration en direct doit tenir). Les versions vectorisées tournent sur ces mêmes 200 simulations pour comparer les temps, puis sur 2 000 pour la distribution.

import time
import numpy as np
import matplotlib.pyplot as plt

N_POLICES = 5000
LAMBDA = 0.1       # fréquence Poisson par police et par an
MU_LN = 7.0        # paramètre mu de la log-normale
SIGMA_LN = 1.2     # paramètre sigma de la log-normale
N_SIM_NAIF = 200   # simulations pour la version naïve et la mesure des temps
N_SIM = 2000       # simulations pour la distribution (version vectorisée)

# Moments théoriques de la Poisson composée
esperance_th = N_POLICES * LAMBDA * np.exp(MU_LN + SIGMA_LN**2 / 2)
variance_th = N_POLICES * LAMBDA * np.exp(2 * MU_LN + 2 * SIGMA_LN**2)
kappa4_th = N_POLICES * LAMBDA * np.exp(4 * MU_LN + 8 * SIGMA_LN**2)  # 4e cumulant

print(f"Portefeuille : {N_POLICES} polices, lambda = {LAMBDA}, "
      f"log-normale (mu = {MU_LN}, sigma = {SIGMA_LN})")
print(f"Coût moyen d'un sinistre     : {np.exp(MU_LN + SIGMA_LN**2 / 2):>12,.0f} EUR")
print(f"Charge totale, espérance     : {esperance_th:>12,.0f} EUR")
print(f"Charge totale, écart-type    : {np.sqrt(variance_th):>12,.0f} EUR")

Étape 1. La version naïve

def monte_carlo_naif(n_polices, lam, mu_ln, sigma_ln, n_sim, seed):
    """Version naïve : boucles sur les simulations, les polices et les sinistres."""
    rng = np.random.default_rng(seed)
    cout_total_par_simulation = np.zeros(n_sim)
    for s in range(n_sim):
        cout_s = 0.0
        for p in range(n_polices):
            nb_sinistres_p = rng.poisson(lam)
            for k in range(nb_sinistres_p):
                cout_s += rng.lognormal(mu_ln, sigma_ln)
        cout_total_par_simulation[s] = cout_s
    return cout_total_par_simulation


t0 = time.perf_counter()
resultats_naif = monte_carlo_naif(N_POLICES, LAMBDA, MU_LN, SIGMA_LN, N_SIM_NAIF, seed=42)
duree_naif = time.perf_counter() - t0
print(f"Version naïve, {N_SIM_NAIF} simulations : {duree_naif:.2f} s")
print(f"Charge moyenne : {resultats_naif.mean():,.0f} EUR")
Version naïve, 200 simulations : 1.17 s
Charge moyenne : 1,119,663 EUR

Trois boucles imbriquées : sur les simulations, sur les polices, sur les sinistres de chaque police. Pour 200 simulations de 5 000 polices, cela fait un million d’appels rng.poisson un par un, plus un appel par sinistre. C’est la version qu’un débutant écrit naturellement.

Étape 2. La version vectorisée, puis sans aucune boucle

La première vectorisation tire tous les nombres de sinistres en un seul appel (un tableau simulations × polices), puis tous les coûts en un seul appel. Il reste une boucle Python, courte : une somme par simulation.

def monte_carlo_vectorise(n_polices, lam, mu_ln, sigma_ln, n_sim, seed):
    """Tirages en bloc ; reste une boucle Python sur les simulations pour sommer."""
    rng = np.random.default_rng(seed)
    n_sinistres = rng.poisson(lam, size=(n_sim, n_polices))
    par_simulation = n_sinistres.sum(axis=1)
    couts = rng.lognormal(mu_ln, sigma_ln, size=par_simulation.sum())
    fin = par_simulation.cumsum()
    debut = np.concatenate([[0], fin[:-1]])
    return np.array([couts[d:f].sum() for d, f in zip(debut, fin)])

La variante np.bincount supprime cette dernière boucle. Chaque coût reçoit le numéro de sa simulation (np.repeat), et np.bincount fait la somme des coûts par numéro. Le même geste agrège par police, par segment ou par année : c’est le pattern à retenir.

def monte_carlo_bincount(n_polices, lam, mu_ln, sigma_ln, n_sim, seed):
    """Tirages en bloc et somme par simulation avec np.bincount : aucune boucle Python."""
    rng = np.random.default_rng(seed)
    n_sinistres = rng.poisson(lam, size=(n_sim, n_polices))
    par_simulation = n_sinistres.sum(axis=1)
    couts = rng.lognormal(mu_ln, sigma_ln, size=par_simulation.sum())
    num_simulation = np.repeat(np.arange(n_sim), par_simulation)
    return np.bincount(num_simulation, weights=couts, minlength=n_sim)


# Mêmes tirages dans le même ordre : les deux variantes doivent coïncider
a = monte_carlo_vectorise(N_POLICES, LAMBDA, MU_LN, SIGMA_LN, N_SIM_NAIF, seed=42)
b = monte_carlo_bincount(N_POLICES, LAMBDA, MU_LN, SIGMA_LN, N_SIM_NAIF, seed=42)
print(f"Les deux variantes vectorisées coïncident : {np.allclose(a, b, rtol=1e-12)}")
Les deux variantes vectorisées coïncident : True

Étape 3. Mesurer le gain

On compare à taille égale (200 simulations). Un temps court est sensible à tout ce qui tourne en même temps sur le poste : pour les versions vectorisées, on garde le meilleur de cinq passages.

def meilleur_temps(fonction, repetitions=5, **kwargs):
    temps = []
    for _ in range(repetitions):
        t0 = time.perf_counter()
        fonction(**kwargs)
        temps.append(time.perf_counter() - t0)
    return min(temps)


params = dict(n_polices=N_POLICES, lam=LAMBDA, mu_ln=MU_LN, sigma_ln=SIGMA_LN,
              n_sim=N_SIM_NAIF, seed=42)
duree_vec = meilleur_temps(monte_carlo_vectorise, **params)
duree_bc = meilleur_temps(monte_carlo_bincount, **params)


def tirage_poisson_seul(n_polices, lam, n_sim, seed, **autres):
    """Le seul tirage du tableau simulations x polices, sans les coûts ni la somme."""
    return np.random.default_rng(seed).poisson(lam, size=(n_sim, n_polices))


duree_tirage = meilleur_temps(tirage_poisson_seul, **params)

print(f"Temps pour {N_SIM_NAIF} simulations de {N_POLICES} polices :")
print(f"  naïve                : {duree_naif:8.3f} s")
print(f"  vectorisée           : {duree_vec:8.3f} s   (rapport x{duree_naif / duree_vec:.0f})")
print(f"  vectorisée, bincount : {duree_bc:8.3f} s   (rapport x{duree_naif / duree_bc:.0f})")
print(f"  dont tirage Poisson  : {duree_tirage:8.3f} s")

Mesuré le 13 octobre 2026 sur le poste de rédaction (un portable à processeur Intel Core i7-8550U, occupé en même temps par d’autres calculs), en sept séries : la version naïve a pris de 3 secondes, poste peu chargé, à près de 30 secondes, poste saturé ; les versions vectorisées, moins de deux dixièmes de seconde ; le rapport est allé de 53 à 188 selon la série. La version naïve, mesurée sur un seul passage, varie bien plus d’une série à l’autre que les vectorisées, mesurées sur le meilleur de cinq : c’est surtout elle qui fait bouger le rapport. Les deux variantes vectorisées font jeu égal, et la dernière ligne dit pourquoi : le seul tirage du tableau de 200 × 5 000 nombres de sinistres prend l’essentiel du temps, la somme finale presque rien. Le rapport du bloc ci-dessus est celui de la machine qui a rendu cette page.

Le gain ne se déclare pas, il se mesure : un rapport de temps ne vaut que pour la machine, la taille et le code qui l’ont produit, et il s’écrit avec eux. Et la mémoire limite la taille : le tableau des nombres de sinistres occupe 8 octets par case.

Au-delà de quelques gigaoctets, on vectorise par paquets de simulations (une boucle externe sur des blocs de quelques centaines de simulations), au lieu d’un seul tableau.

Étape 4. Vérifier que le modèle n’a pas changé

La même graine ne suffit pas à comparer les deux versions : la naïve tire un Poisson, puis ses coûts, puis le Poisson suivant ; la vectorisée tire tous les Poisson puis tous les coûts. Le générateur est consommé dans un autre ordre, les tirages diffèrent, et les résultats aussi. La graine rend chaque version reproductible ; elle ne rend pas les deux comparables tirage à tirage.

Le juge est donc le modèle lui-même. Pour chaque version, on compare la moyenne et la variance simulées aux valeurs théoriques, en nombre d’erreurs-types (l’erreur-type de la variance empirique vaut environ \(\sqrt{(\kappa_4 + 2\operatorname{Var}[S]^2)/n}\), avec \(\kappa_4 = N\lambda\,e^{4\mu + 8\sigma^2}\) le quatrième cumulant de la charge).

resultats_vec = monte_carlo_bincount(N_POLICES, LAMBDA, MU_LN, SIGMA_LN, N_SIM, seed=42)


def controle_moments(nom, x):
    n = len(x)
    z_moy = (x.mean() - esperance_th) / np.sqrt(variance_th / n)
    se_var = np.sqrt((kappa4_th + 2 * variance_th**2) / n)
    z_var = (x.var(ddof=1) - variance_th) / se_var
    print(f"{nom:<22} n = {n:>5}   moyenne {x.mean():>11,.0f} (z = {z_moy:+.2f})   "
          f"écart-type {x.std(ddof=1):>9,.0f} (z variance = {z_var:+.2f})")


print(f"{'Théorie':<22} {'':>9}   moyenne {esperance_th:>11,.0f}              "
      f"écart-type {np.sqrt(variance_th):>9,.0f}")
controle_moments("Naïve", resultats_naif)
controle_moments("Vectorisée (bincount)", resultats_vec)
Théorie                            moyenne   1,126,480              écart-type   103,498
Naïve                  n =   200   moyenne   1,119,663 (z = -0.93)   écart-type    95,592 (z variance = -1.28)
Vectorisée (bincount)  n =  2000   moyenne   1,125,304 (z = -0.51)   écart-type   101,197 (z variance = -1.21)

Les deux versions retombent sur l’espérance et l’écart-type théoriques, à moins de deux erreurs-types (les colonnes z) : c’est ce qu’on attend de deux simulations justes du même modèle.

Ce contrôle a une puissance limitée, qu’il faut connaître. Une vectorisation fausse classique tire un seul coût par police sinistrée et le multiplie par le nombre de sinistres, au lieu d’un coût par sinistre. La moyenne reste juste ; la variance est gonflée d’un facteur \(1 + \lambda\,(1 - e^{-\sigma^2})\). Ce que cela donne ici :

facteur_faux = 1 + LAMBDA * (1 - np.exp(-SIGMA_LN**2))
se_relative_var = np.sqrt((kappa4_th + 2 * variance_th**2) / N_SIM) / variance_th
print(f"Variance de la version fausse / variance juste : {facteur_faux:.3f}")
print(f"Erreur-type relative de la variance ({N_SIM} simulations) : {se_relative_var:.1%}")
print(f"Écart attendu, en erreurs-types : {(facteur_faux - 1) / se_relative_var:.1f}")
Variance de la version fausse / variance juste : 1.076
Erreur-type relative de la variance (2000 simulations) : 3.6%
Écart attendu, en erreurs-types : 2.1

Une variance gonflée de 7,6 % pour une erreur-type de 3,6 % : l’écart attendu n’est que de deux erreurs-types environ, et le hasard d’une graine peut le faire passer sous le seuil. Pour trancher, on augmente le nombre de simulations du contrôle, ou on contrôle sur un cas où l’erreur pèse plus (une fréquence plus forte).

Reste la queue de distribution. Le quantile à 99,5 % estimé sur 2 000 simulations repose sur la dizaine de valeurs les plus hautes : il bouge d’une graine à l’autre, avec la même version et le même modèle. Avant de comparer les quantiles de deux versions, on mesure ce bruit.

q995 = {}
for graine in [42, 43, 44]:
    x = monte_carlo_bincount(N_POLICES, LAMBDA, MU_LN, SIGMA_LN, N_SIM, seed=graine)
    q995[graine] = np.percentile(x, 99.5)
    print(f"Version vectorisée, graine {graine} : quantile 99,5 % = {q995[graine]:,.0f} EUR")
etendue = (max(q995.values()) - min(q995.values())) / np.mean(list(q995.values()))
print(f"Écart entre graines, même code : {etendue:.1%} du quantile moyen")
Version vectorisée, graine 42 : quantile 99,5 % = 1,398,294 EUR
Version vectorisée, graine 43 : quantile 99,5 % = 1,466,014 EUR
Version vectorisée, graine 44 : quantile 99,5 % = 1,426,833 EUR
Écart entre graines, même code : 4.7% du quantile moyen

Un écart de quelques pour cent entre les quantiles de deux versions n’est donc pas un signe de bug à cette taille de simulation : c’est l’ordre de grandeur du bruit, visible ici sur une seule et même version. Pour un quantile réglementaire, on augmente le nombre de simulations jusqu’à ce que ce bruit devienne acceptable, et on le dit.

Exercice : trouvez l’erreur

Un collègue a vectorisé son Monte Carlo et rédige sa validation ainsi :

“J’ai lancé les deux versions avec la même graine 42, 2 000 simulations chacune. Les moyennes diffèrent (1 127 911 contre 1 125 304 EUR) : il y a donc un bug quelque part. J’ai quand même fait un test de Kolmogorov-Smirnov : p = 0,67 > 0,05, donc les deux distributions sont équivalentes et la version vectorisée est validée. Le quantile à 99,5 % diffère de 4,6 %, mais c’est dans la tolérance.”

Relevez ce qui ne va pas dans ce raisonnement.

Voir la réponse
  1. La même graine ne rend pas les deux versions comparables tirage à tirage. Les deux versions consomment le générateur dans un ordre différent. Des moyennes différentes sont donc normales ; elles ne signalent pas un bug. Ce qu’il faut regarder, c’est l’écart de chaque moyenne à l’espérance théorique, en erreurs-types (la seconde moyenne est celle de la version vectorisée à l’étape 4) :
se_moyenne = np.sqrt(variance_th / 2000)
print(f"Erreur-type de la moyenne sur 2 000 simulations : {se_moyenne:,.0f} EUR")
for nom, moyenne in [("naïve", 1_127_911), ("vectorisée", 1_125_304)]:
    print(f"Moyenne {nom:<10} : {(moyenne - esperance_th) / se_moyenne:+.2f} erreur-type de l'espérance")
Erreur-type de la moyenne sur 2 000 simulations : 2,314 EUR
Moyenne naïve      : +0.62 erreur-type de l'espérance
Moyenne vectorisée : -0.51 erreur-type de l'espérance

Les deux moyennes sont à moins d’une erreur-type de l’espérance, de part et d’autre : parfaitement compatibles avec le modèle. 2. Un \(p > 0{,}05\) ne prouve pas l’équivalence. Il dit seulement que le test n’a pas détecté de différence avec ces échantillons. Avec peu de simulations, un test KS laisse passer des écarts réels, notamment dans la queue, là où se joue un quantile à 99,5 %. Le contrôle informatif est la comparaison aux moments théoriques, qui existent ici ; et, faute de théorie, la comparaison à une version de référence sur un nombre de simulations suffisant. 3. Le 4,6 % sur le quantile n’est ni un bug ni « dans la tolérance » : il n’a pas été mesuré contre le bruit. Aucune tolérance n’avait été fixée à l’avance. L’étape 4 montre qu’avec 2 000 simulations, le quantile varie déjà de quelques pour cent d’une graine à l’autre avec le même code. Il faut mesurer ce bruit avant de juger un écart, et augmenter le nombre de simulations si le quantile doit servir. 4. Et une conclusion en creux : le collègue écrit « il y a un bug » puis « validé » sans rien corriger entre les deux. Une validation qui peut conclure dans les deux sens sur les mêmes chiffres ne contrôle rien.

Pièges typiques

  • Croire que la même graine rend les versions comparables tirage à tirage. Elle rend chaque version reproductible. Dès que l’ordre des tirages change, les résultats changent. Comparez chaque version aux moments théoriques, ou à une référence sur beaucoup de simulations.
  • Lire « \(p > 0{,}05\) » comme une preuve d’équivalence. Un test qui ne rejette pas ne démontre rien. Préférez un contrôle dont on connaît la cible (espérance, variance) et une tolérance en erreurs-types fixée avant de regarder.
  • Vectoriser à l’aveugle. Le LLM peut proposer une vectorisation plus lente (tableaux énormes inutiles) ou fausse (un coût par police au lieu d’un par sinistre : la moyenne reste juste, la variance non). Toujours mesurer le temps et contrôler les moments après vectorisation. Si le gain n’est pas là, demander : “pourquoi cette version n’est-elle pas plus rapide ?”.
  • Annoncer un gain qu’on n’a pas mesuré. Un rapport de temps dépend de la machine, de sa charge, de la taille et du code. Donner la mesure, la machine et la taille, ou ne rien donner.
  • Oublier la mémoire. Un tableau simulations × polices de 1 million de polices et 10 000 simulations pèse 80 Go en entiers 64 bits (étape 3). Au-delà de quelques Go, vectoriser par paquets de simulations.
  • Sacrifier la lisibilité. Une version compacte illisible pour un gain marginal n’est pas un bon investissement. Préférer une version claire, un peu plus longue, que le successeur relira.

Variantes et cas connexes

  • R4 Bootstrap Chain-Ladder : un vrai bootstrap (rééchantillonnage des résidus), avec des boucles sur simulations qui peuvent se vectoriser de la même façon.
  • I1 Migration d’un calcul Excel-VBA en module Python : un classeur migré en Python est souvent l’occasion de vectoriser, avec la même règle : valider avant de basculer.
  • I3 Tests pytest : un Monte Carlo vectorisé mérite des tests qui vérifient la reproductibilité (même graine, même résultat, pour une même version), l’accord avec les moments théoriques à une tolérance en erreurs-types, et les cas limites (n_polices=0, lam=0).

Pour aller plus loin

  • Utiliser la structure du modèle. Si toutes les polices ont la même fréquence, le nombre total de sinistres d’une simulation suit directement une loi de Poisson de paramètre \(N\lambda\) : un tirage par simulation au lieu de 5 000, et le tableau simulations × polices disparaît. Ce raccourci ne vaut plus dès que les fréquences diffèrent d’une police à l’autre ; il se valide, lui aussi, par les moments.
  • Numba (@njit) compile une boucle Python en code natif, sans réécrire en vectorisé. Utile quand la vectorisation est difficile à exprimer. Le gain se mesure comme ici.
  • JAX (calcul sur GPU si disponible) et Dask (calcul réparti sur plusieurs machines), quand un seul poste ne suffit plus.
