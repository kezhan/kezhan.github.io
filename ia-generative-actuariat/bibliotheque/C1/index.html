C1. Dashboard sinistralité auto avec Lovable

Cette fiche illustre la démarche D sur Lovable, avec sa version locale par Claude Code. Ce que vous apprenez n’est pas la sinistralité, mais comment décrire la spec d’un dashboard en langage naturel, comment préparer une donnée synthétique ou agrégée avant de la confier à un service tiers, et comment valider les chiffres affichés contre la référence Python.

La démarche se pratique en direct dans l’atelier de la demi-journée « Communication et tableaux de bord » du support.

Le contexte métier

Le pilotage actuariel demande des tableaux de bord vivants : KPI globaux, drill-down par segment, alertes sur les segments qui dérivent, partagés avec les équipes commerciales et la direction. Streamlit ou Dash les construisent en Python ; encore faut-il écrire ce Python, et soigner la mise en page.

Lovable (lancé fin 2024, issu du projet GPT Engineer) génère des applications web (React, Tailwind) à partir de descriptions en langage naturel. L’actuaire décrit le dashboard en français, Lovable écrit l’application, l’héberge et la publie à une adresse web. C’est rapide pour une maquette ou une démonstration. C’est aussi un service externe : les données qu’on lui donne partent chez lui, et les calculs qu’il affiche sont écrits par lui.

La même spec, donnée à Claude Code, produit une version locale (une page HTML autonome ou une application Streamlit) dont les calculs restent en Python sur votre poste. La fiche montre les deux.

Ce cas illustre l’organisation des données (export propre, dictionnaire des colonnes, agrégats plutôt que lignes), l’interface de présentation (KPI, drill-down, alertes), la gouvernance (hébergement, entraînement des modèles, données synthétiques en formation), et le pilotage IA (5 prompts d’intention, itération visuelle, vérification des chiffres).

Donnée d’entrée

On simule un portefeuille auto de 30 000 polices sur un exercice. L’exposition (la part de l’année pendant laquelle la police a couru) va de 0,1 à 1 : une police présente trois mois n’a acquis qu’un quart de sa prime annuelle. Le profil de risque suit la réalité du marché dans ses grandes lignes : fréquence en U selon l’âge, jeunes conducteurs les plus risqués, fréquence croissante avec le coefficient bonus-malus. Le tarif simulé suit l’âge et le bonus-malus mais ignore la région : c’est lui qui fera apparaître des écarts de S/P par région.

import numpy as np
import pandas as pd
import matplotlib.pyplot as plt
from pathlib import Path

rng = np.random.default_rng(42)
N = 30_000
REGIONS = ["Île-de-France", "Auvergne-Rhône-Alpes", "Nouvelle-Aquitaine",
           "Occitanie", "Hauts-de-France", "Provence-Alpes-Côte d'Azur"]
CLASSES_BM = np.array([50, 60, 70, 80, 90, 100, 120, 150, 200, 300])  # CRM x 100

age = rng.integers(18, 86, size=N)
bonus_malus = rng.choice(CLASSES_BM, size=N,
                         p=[0.30, 0.15, 0.12, 0.10, 0.08, 0.10, 0.07, 0.04, 0.03, 0.01])
# Un conducteur ne descend sous 100 qu'avec les années : 0,95 par an sans sinistre
bm_minimum = 100 * 0.95 ** (age - 18)
bonus_malus = np.maximum(bonus_malus, CLASSES_BM[np.searchsorted(CLASSES_BM, bm_minimum)])
region = rng.choice(REGIONS, size=N, p=[0.25, 0.18, 0.12, 0.15, 0.15, 0.15])
exposition = rng.uniform(0.1, 1.0, size=N).round(3)

# Risque simulé : en U sur l'âge, croissant avec le bonus-malus, niveau propre à chaque région
effet_age = 0.9 * np.exp(-(age - 18) / 7) + 0.02 * np.clip(age - 70, 0, None)
niveau_region = pd.Series([1.25, 0.95, 0.95, 1.00, 1.10, 1.10], index=REGIONS)
lam = 0.055 * np.exp(effet_age) * (bonus_malus / 100) ** 0.8 * niveau_region[region].to_numpy()
nb_sinistres = rng.poisson(lam * exposition)

# Un coût tiré pour chaque sinistre, puis sommé par police
couts = rng.lognormal(7.6, 1.0, size=nb_sinistres.sum())
cout_sinistres = np.bincount(np.repeat(np.arange(N), nb_sinistres), weights=couts, minlength=N)

# Tarif : suit l'âge et le bonus-malus, ignore la région
prime_pure_tarif = 0.055 * np.exp(effet_age) * (bonus_malus / 100) ** 0.8 * np.exp(7.6 + 0.5)
prime_annuelle = np.clip((1.05 * prime_pure_tarif + 90) * rng.lognormal(0, 0.1, size=N),
                         150, 3000).round(0)

polices = pd.DataFrame({
    "police_id": [f"POL_{i:06d}" for i in range(N)],
    "age": age,
    "bonus_malus": bonus_malus,
    "region": region,
    "exposition": exposition,
    "prime_annuelle": prime_annuelle,
    "prime_acquise": (prime_annuelle * exposition).round(2),
    "nb_sinistres": nb_sinistres,
    "cout_sinistres": cout_sinistres.round(0),
})

primes_acquises = polices["prime_acquise"].sum()
charge = polices["cout_sinistres"].sum()
print(f"Polices : {len(polices):,}")
print(f"Exposition : {polices['exposition'].sum():,.0f} années-police")
print(f"Primes acquises : {primes_acquises:,.0f} EUR")
print(f"Charge sinistres : {charge:,.0f} EUR")
print(f"Fréquence : {polices['nb_sinistres'].sum() / polices['exposition'].sum():.2%}")
print(f"S/P (charge / primes acquises) : {charge / primes_acquises:.1%}")
Polices : 30,000
Exposition : 16,541 années-police
Primes acquises : 4,707,594 EUR
Charge sinistres : 3,172,358 EUR
Fréquence : 5.74%
S/P (charge / primes acquises) : 67.4%

Le S/P se calcule sur les primes acquises (prime annuelle × exposition) : c’est la prime qui correspond à la période où les sinistres ont pu survenir. Le fichier porte donc une colonne prime_acquise toute faite, pour qu’aucune application n’ait à la recalculer.

EXPORT_DIR = Path("_resources")
EXPORT_DIR.mkdir(exist_ok=True)
chemin = EXPORT_DIR / "polices_synthetiques.csv"
polices.to_csv(chemin, index=False)
print(f"Export : {chemin}")
print(f"Taille : {chemin.stat().st_size / 1024:.0f} KB")

Corrigé pas à pas

Étape 1. Préparer les données et les chiffres de référence

Lovable comme Claude Code lisent du CSV ou du JSON. On veut un export propre :

  • Pas de données nominatives. Ici tout est synthétique ; sur de vraies données, remplacer le numéro de contrat par POL_xxx est une pseudonymisation, pas une anonymisation : les données restent personnelles au sens du RGPD, car l’âge, la région, le bonus-malus et les sinistres suffisent parfois à retrouver quelqu’un.
  • Pas de NaN (on remplit avec 0 ou une valeur sentinelle documentée).
  • Des noms de colonnes sans accent ni espace, et un dictionnaire des colonnes (unité, sens) donné dans le premier prompt.
  • Les grandeurs déjà calculées quand une erreur est probable (ici prime_acquise).

Étape 2. Anatomie d’un dashboard actuariel : KPI, drill-down, alertes

Trois types de vues, une par page.

KPI globaux (page d’accueil).

  • Cartes avec chiffre clé en gros, libellé court, et écart à N-1 ou à la cible.
  • Une poignée de KPI sur la page d’accueil (trois à six).
  • Couleur conditionnelle (vert si OK, ambre si vigilance, rouge si alerte).

Drill-down (page de pilotage).

  • Sélecteurs multi-valeurs (régions, segments).
  • Tableau croisé avec coloration conditionnelle, et l’exposition à côté du S/P : un S/P sur 30 années-police ne dit presque rien.
  • Possibilité d’exporter le résultat filtré en CSV ou en PDF.

Alertes (page de surveillance).

  • Liste des segments à examiner.
  • Chaque alerte : segment, S/P, seuil, volume, lien vers le drill-down concerné.
  • Un volume minimal, sinon les alertes sont du bruit.

Les chiffres de ces trois pages, on les calcule d’abord en Python : ce sont eux que le dashboard devra afficher.

def profil(df, par):
    g = df.groupby(par, observed=True).agg(
        polices=("police_id", "size"),
        exposition=("exposition", "sum"),
        primes_acquises=("prime_acquise", "sum"),
        charge=("cout_sinistres", "sum"),
        sinistres=("nb_sinistres", "sum"),
    )
    g["frequence"] = g["sinistres"] / g["exposition"]
    g["sp"] = g["charge"] / g["primes_acquises"]
    return g

Étape 4. Workflow de construction (en pratique)

L’itération se fait en cycles courts, avec Lovable comme avec Claude Code.

  1. Premier prompt : la vue d’ensemble et les règles de calcul. L’outil génère un squelette.
  2. Connecter les données. Avec Lovable, deux gestes différents. Un CSV joint au chat devient une entrée du modèle : il part chez Lovable et chez les fournisseurs d’IA qu’il utilise, et Lovable peut en recopier des lignes dans le code de l’application. Un CSV chargé dans l’application vit là où l’application le range : dans le navigateur de celui qui le charge, si la page lit un fichier local, ou dans la base Lovable Cloud, si vous l’y importez. Vérifier ensuite que les colonnes sont reconnues avec le bon sens (exposition, prime acquise).
  3. Itérations visuelles : “agrandis le titre”, “passe le bleu en bleu nuit”, “supprime la carte en haut à droite”.
  4. Itérations fonctionnelles : “ajoute un filtre par tranche d’âge”, “exporte en CSV”.
  5. Validation par l’actuaire : ouvrir le dashboard et comparer les chiffres à la référence de l’étape 1, puis une case du tableau croisé et une alerte à l’étape 2.
  6. Partage : vérifier qui peut ouvrir l’adresse publiée avant de la diffuser.

Étape 5. Limites à connaître avant de mettre en production

  • Où vont les données. Selon la page sécurité de Lovable (lovable.dev/security, consultée le 29 septembre 2026) : Lovable Cloud héberge les données dans la région choisie, UE, US ou Asie-Pacifique ; les prompts, le code et les données des offres Business et Enterprise ne servent pas à entraîner les modèles ; les abonnés Free et Pro peuvent désactiver l’entraînement dans les réglages de leur compte, ce qui veut dire qu’il est actif tant qu’ils ne l’ont pas fait. Lovable propose un contrat de traitement des données (DPA). Sans ce contrat signé par votre organisation, et sans une offre Business ou Enterprise, aucune donnée réelle.
  • Le calcul est écrit par Lovable. L’application agrège les données en JavaScript : chaque S/P affiché est un calcul que Lovable a écrit et que vous n’avez pas relu. Pour un calcul actuariel (Chain-Ladder, GLM, projections), faire le calcul en Python, exporter les résultats, et laisser l’application afficher, soit par un fichier d’agrégats, soit par une API que vous exposez (FastAPI par exemple).
  • Versionnement. Lovable garde un historique des versions et peut synchroniser le code avec un dépôt GitHub. Pour un projet qui dure, versionner ce code comme le reste (annexe E).
  • Coût récurrent. L’abonnement court tant que l’application doit rester en ligne. Pour un dashboard gardé plusieurs années, comparer avec une version locale.
  • Évolution rapide de l’outil. Offres, hébergement et conditions changent vite. Relire la page sécurité et les conditions avant chaque nouveau projet, pas seulement la première fois.

Pièges typiques

  • Données réelles jointes au chat par inadvertance. Un fichier joint au chat part chez le fournisseur dès l’envoi. Préparer l’export synthétique ou agrégé avant d’ouvrir Lovable, et garder les fichiers réels hors du dossier de travail.
  • Prendre un identifiant POL_xxx pour une anonymisation. Sur de vraies données, c’est une pseudonymisation : le RGPD s’applique toujours.
  • Laisser l’outil deviner les règles de calcul. Sans dictionnaire des colonnes ni formule, une application peut sommer des taux ou faire la moyenne de ratios au lieu de rapporter une somme à une somme. Les règles de calcul vont dans le premier prompt, et les chiffres affichés se comparent à la référence Python.
  • Des alertes sans volume minimal. Un S/P de 95 % sur quelques dizaines d’années-police est du bruit. Afficher l’exposition à côté de chaque S/P.
  • Trop d’éléments sur une page. Un dashboard avec 25 KPI sur la page d’accueil est illisible. Une poignée de KPI principaux, le reste va en drill-down ou en alertes.

Exercice : trouvez les erreurs

Un collègue a construit le dashboard avec une version antérieure des prompts. Sa page 1 affiche un S/P global de 37,1 %, un classement où aucune région ne dépasse 48 %, donc aucune alerte, et une belle courbe du S/P mensuel sur les douze derniers mois. Sans ouvrir son code, à partir de ces seuls symptômes et de la référence de l’étape 1 : qu’est-ce qui ne va pas ? Pour le S/P, allez plus loin qu’un « c’est faux » : le rapport entre son 37,1 % et le S/P de référence correspond à une grandeur du portefeuille. Laquelle, et qu’en déduisez-vous sur son calcul ?

Voir la réponse

Deux erreurs, et la seconde est plus grave que la première.

  1. Le S/P est rapporté aux primes annuelles. Les expositions vont de 0,1 à 1 : une police présente trois mois a acquis un quart de sa prime. Diviser la charge par la prime annuelle sous-estime le S/P et fait disparaître les alertes. Le rapport des deux S/P le dit sans ouvrir le code : la charge est la même des deux côtés, donc ce rapport vaut la somme des primes acquises divisée par la somme des primes annuelles, l’exposition moyenne pondérée par la prime.
primes_annuelles = polices["prime_annuelle"].sum()
print(f"Global : {charge / primes_annuelles:.1%} sur primes annuelles, "
      f"{charge / primes_acquises:.1%} sur primes acquises")
print(f"Rapport des deux S/P                    : {(charge / primes_annuelles) / (charge / primes_acquises):.3f}")
print(f"Primes acquises / primes annuelles      : {primes_acquises / primes_annuelles:.3f}")
print(f"Exposition moyenne (non pondérée)       : {polices['exposition'].mean():.3f}")
print()
sp_annuel = polices.groupby("region")["cout_sinistres"].sum() / polices.groupby("region")["prime_annuelle"].sum()
comparaison = pd.DataFrame({"S/P sur primes annuelles (faux)": sp_annuel,
                            "S/P sur primes acquises": par_region["sp"]}).round(3)
print(comparaison.sort_values("S/P sur primes acquises", ascending=False).to_string())

  1. La courbe mensuelle est inventée. Le fichier n’a ni date d’effet ni date de survenance. Une courbe par mois ne peut venir que d’une série fabriquée par l’outil (répartition uniforme, données d’exemple, ou pire, valeurs plausibles). Pour une trajectoire mensuelle, il faut une date de survenance par sinistre et l’exposition mois par mois, et le calcul se fait en Python avant d’être affiché.

La leçon est la même pour les deux : les règles de calcul et le périmètre des données s’écrivent dans le prompt, et un chiffre affiché se compare à la référence avant d’être cru.
