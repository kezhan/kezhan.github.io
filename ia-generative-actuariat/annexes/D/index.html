Annexe D. settings.json pour un cabinet : permissions, bac à sable, hooks

Le fichier .claude/settings.json règle ce que Claude Code fait sans demander, ce pour quoi il demande toujours, et ce qu’il refuse. Bien réglé, il supprime la fatigue de validation et évite les accidents : une suppression, un push, un appel réseau partis sans qu’on y pense. Il ne protège pas des données. Cette annexe décrit la mécanique réelle (état au 29 septembre 2026, d’après la documentation officielle), donne un point de départ commenté, puis ce qui protège vraiment.

  • Elles ne protègent pas des données : un deny Read n’empêche pas un script Python autorisé d’ouvrir le fichier et d’en afficher le contenu.
  • Seul le bac à sable arrête ce script, et il n’existe pas sous Windows natif.
  • Les données sensibles restent donc hors du dossier de travail ; on travaille sur des données synthétiques ou pseudonymisées.
  • Tout ce que Claude lit ou affiche part chez le fournisseur. Seule une offre entreprise (Team, Enterprise, API avec contrat) fait du fournisseur un sous-traitant au sens du RGPD.

Comment Claude Code décide

Deux choses décident de ce que Claude fait seul : le mode, et les règles.

Le mode. En mode default (Manuel), Claude lit librement dans le dossier du projet et demande avant de modifier un fichier ou de lancer une commande. acceptEdits accepte en plus les modifications de fichiers ; plan lit et propose sans rien modifier ; auto confie l’examen de chaque action à un second modèle, qui laisse passer ce qu’il juge conforme à votre demande et bloque le reste ; dontAsk refuse tout ce qui demanderait un accord, sauf ce que les règles autorisent ; bypassPermissions ne demande plus rien, et n’a sa place que dans un environnement isolé. Depuis la version 2.1.283, auto est le mode de départ par défaut dans le terminal et dans VS Code. Le réglage defaultMode choisit le mode de départ, et la DSI peut interdire les modes auto et bypassPermissions (disableAutoMode, disableBypassPermissionsMode).

Les règles. Trois listes : allow (sans demander), ask (toujours demander), deny (jamais). Claude Code les examine dans cet ordre : deny, puis ask, puis allow, et la première règle qui correspond décide. La précision d’une règle ne change pas cet ordre : un allow ne peut pas découper d’exception dans un deny, et un ask demande même si un allow plus précis correspond aussi. Cela vaut entre fichiers : un deny écrit à n’importe quel niveau bloque un allow écrit à n’importe quel autre. En mode auto, les règles s’appliquent toujours : un ask demande, même quand le second modèle laisserait passer.

Ce qui n’a pas besoin de règle. Lire un fichier du projet ne demande pas d’accord, en mode Manuel non plus. Une série de commandes reconnues en lecture seule (ls, cat, head, tail, grep, wc, les formes de git qui ne modifient rien) passe sans demande dans tous les modes. Autoriser Read(**), Glob(**), Grep(**) ou cat ne sert donc à rien.

Les quatre niveaux de réglages

Niveau Fichier Qui l’écrit Portée
Géré managed-settings.json : C:\Program Files\ClaudeCode\ sous Windows, /Library/Application Support/ClaudeCode/ sous macOS, /etc/claude-code/ sous Linux et WSL ; ou le registre Windows La DSI Tous les utilisateurs du poste ; ne se contourne pas
Local .claude/settings.local.json Vous Ce projet, sur votre seul poste, hors Git
Projet .claude/settings.json L’équipe Ce projet, pour tous ceux qui le clonent ; versionné
Utilisateur ~/.claude/settings.json Vous Tous vos projets

L’ordre de priorité, du plus fort au plus faible : géré, puis les options passées en ligne de commande, puis local, projet, utilisateur. Une politique commune à tout le cabinet passe par le niveau géré : il n’existe ni settings.cabinet.json ni directive d’inclusion d’un fichier de réglages dans un autre.

La forme des règles

Les commandes. Bash(python *) autorise toute commande qui commence par python ; un * final précédé d’une espace couvre aussi la commande seule. L’ancienne écriture Bash(python:*) reste acceptée et veut dire la même chose. Le * se place après la sous-commande : Bash(git commit *) n’autorise que les commits, Bash(git *) autorise tout Git, push compris. Dans une commande composée (a && b), chaque morceau doit correspondre à une règle.

Une règle vise le texte de la commande, pas le programme. Bash(curl *) en deny arrête curl https://…, pas /usr/bin/curl https://…, ni sh -c 'curl …', ni un script Python qui appelle le réseau. Et Bash(python *) autorise n’importe quel script Python, donc toutes les lectures, écritures et connexions que ce script fera. C’est le prix de l’exécution sans demande.

Sous Windows. Claude Code dispose de l’outil PowerShell, dont les règles ont la même forme : PowerShell(python *), PowerShell(Remove-Item *). Sans Git for Windows, c’est son seul outil de commande. Avec Git for Windows, il a aussi l’outil Bash (Git Bash), mais l’outil PowerShell reste actif par défaut avec un compte Claude ou Console, et Claude le traite comme son shell principal. Une règle Bash(...) ne s’applique pas à PowerShell : Bash(rm *) ne couvre pas Remove-Item, et Bash(git reset --hard *) n’arrête pas la même commande lancée depuis PowerShell. D’où les deux familles de règles dans le modèle ci-dessous. Sur un poste qui a Git for Windows, des réglages qui portent un deny Bash(...) et aucune règle PowerShell(...) coupent l’outil PowerShell, pour que rien ne passe par lui. Une règle écrite pour une cmdlet couvre ses alias courants (PowerShell(Get-ChildItem *) couvre ls et dir).

Les fichiers. Les règles sur les chemins s’écrivent avec Read(...) et Edit(...), en syntaxe gitignore. Une règle de chemin sur Write, Glob ou NotebookEdit est acceptée mais jamais consultée : on écrit Edit(docs/**) et Read(docs/**).

Préfixe Sens Exemple
//chemin Absolu, depuis la racine du disque Read(//srv/production/**) ; sous Windows, Read(//c/Donnees/**) pour C:\Donnees
~/chemin Depuis votre dossier personnel Read(~/.aws/**)
/chemin Depuis le dossier lié au fichier de réglages : la racine du projet pour .claude/settings.json, ~/.claude/ pour vos réglages personnels Edit(/src/**)
chemin ou ./chemin Depuis le dossier courant Read(./.env)

Le piège classique : Read(/tmp/donnees/**) ne vise pas le dossier /tmp du disque mais un dossier tmp sous la racine du projet. Le chemin absolu s’écrit Read(//tmp/donnees/**).

Le web. WebFetch(domain:raw.githubusercontent.com) autorise l’outil de lecture web de Claude sur un domaine. Pour restreindre le réseau, on interdit curl et wget et on autorise des domaines par WebFetch(domain:…), plutôt que d’écrire des règles curl par adresse, qui se contournent par une option ou une redirection.

Un point de départ pour un projet actuariel

À placer dans .claude/settings.json, à la racine du projet, puis à commiter : l’équipe en hérite.

{
  "permissions": {
    "allow": [
      "Bash(python *)",
      "Bash(pytest *)",
      "Bash(git add *)",
      "Bash(git commit *)",
      "PowerShell(python *)",
      "PowerShell(pytest *)",
      "PowerShell(git add *)",
      "PowerShell(git commit *)"
    ],
    "ask": [
      "Bash(git push *)",
      "PowerShell(git push *)"
    ],
    "deny": [
      "Bash(rm *)",
      "Bash(curl *)",
      "Bash(wget *)",
      "Bash(ssh *)",
      "Bash(scp *)",
      "Bash(sudo *)",
      "Bash(git reset --hard *)",
      "Bash(git clean *)",
      "Bash(git push --force *)",
      "PowerShell(Remove-Item *)",
      "PowerShell(Invoke-WebRequest *)",
      "PowerShell(Invoke-RestMethod *)",
      "PowerShell(ssh *)",
      "PowerShell(scp *)",
      "PowerShell(git reset --hard *)",
      "PowerShell(git clean *)",
      "PowerShell(git push --force *)",
      "Read(./.env)",
      "Read(./.env.*)",
      "Read(./secrets/**)"
    ]
  }
}

Lecture en clair.

  • Sans demander : lancer Python et pytest, préparer et faire un commit. Lire, chercher, consulter l’état de Git passent déjà sans règle.
  • Toujours demander : git push. Envoyer le travail sur le serveur partagé reste une décision humaine, même en mode auto.
  • Jamais : supprimer par rm ou Remove-Item, appeler le réseau par curl, wget, Invoke-WebRequest ou Invoke-RestMethod, se connecter à une autre machine (ssh, scp), élever ses droits par sudo, effacer l’historique ou les fichiers non suivis (git reset --hard, git clean), forcer un push. Chaque refus existe en Bash(...) et en PowerShell(...), sauf sudo, propre à Bash. Le deny sur git push --force passe avant le ask sur git push : le push simple demande, le push forcé est refusé.
  • Le fichier .env et le dossier secrets/ : l’outil de lecture de Claude ne les ouvre pas, ni cat, ni une redirection. Un script Python, si.
  • Tout le reste suit le mode : en mode Manuel, Claude demande ; en mode auto, le second modèle décide.

Ces règles visent la forme habituelle de chaque commande, et une variante leur échappe. git push origin main --force ne correspond pas au deny git push --force * : il tombe sur le ask git push *, qui demande au lieu de refuser. git -C . push ne correspond à aucune des deux règles et retombe dans le mode. Elles évitent l’accident courant ; elles ne sont pas une enceinte.

On peut ajouter un deny Read sur un dossier de données (Read(./donnees/**)) : c’est un garde-fou contre l’ouverture par mégarde avec l’outil de lecture, pas une protection. Les données sensibles n’ont rien à faire dans ce dossier.

TipExercice : ce réglage protège-t-il les données ?

Un collègue garde "Bash(python *)" dans allow et ajoute "Read(./data/clients_nominatifs/**)" dans deny. Il annonce à l’équipe : « Claude ne pourra plus lire ces fichiers, même si on le lui demande. On peut laisser les données d’assurés dans le projet. » A-t-il raison ?

Voir la réponse

Non. Le deny Read empêche l’outil de lecture de Claude Code, les commandes de lecture qu’il reconnaît (cat, head, tail, sed, tee) et les redirections d’ouvrir ces fichiers. Il ne s’applique pas à un programme qui ouvre le fichier lui-même, comme un script Python. Or Bash(python *) autorise n’importe quel script :

import pandas as pd
print(pd.read_csv("data/clients_nominatifs/assures.csv").head())

Claude peut écrire ce script, le lancer sans demander et lire la sortie : les cinq premières lignes partent chez le fournisseur. Seul le bac à sable bloquerait la lecture, et il n’existe pas sous Windows natif. La bonne réponse : sortir les données nominatives du dossier de travail, et travailler sur un jeu synthétique ou pseudonymisé.

Variantes

Exploration personnelle

Pour vos explorations sur données publiques, des autorisations en plus, dans .claude/settings.local.json (hors Git, pour vous seul) :

{
  "permissions": {
    "allow": [
      "Bash(jupyter *)",
      "Bash(streamlit run *)",
      "Bash(quarto render *)",
      "WebFetch(domain:raw.githubusercontent.com)"
    ]
  }
}

La dernière ligne autorise Claude à lire des fichiers publics sur GitHub (un jeu de données ouvert, par exemple) par son outil web. Un curl vers ce domaine resterait refusé : le deny Bash(curl *) du fichier de l’équipe passe avant tout allow, quel que soit le fichier qui le porte.

Production verrouillée

Pour un projet de production, l’idée est de nommer ce qui est permis et de refuser tout le reste sans demander. C’est le rôle du mode dontAsk :

{
  "permissions": {
    "defaultMode": "dontAsk",
    "allow": [
      "Edit(./src/**)",
      "Edit(./tests/**)",
      "Bash(python -m pytest *)",
      "Bash(python -m mypy src)"
    ]
  }
}

Claude lit le projet, modifie le code et les tests, lance les tests et la vérification de types. Toute autre action qui demanderait un accord est refusée d’office.

TipExercice : pourquoi ce réglage bloque-t-il tout ?

Une ancienne version de cette annexe proposait, pour la production, d’autoriser Bash(pytest:*) et quelques commandes Git en lecture, avec "deny": ["Bash(*)"] pour « interdire tout le reste ». Que se passe-t-il ?

Voir la réponse

Bash(*) équivaut à Bash : en deny, il retire l’outil Bash entier. Et le deny passe avant l’allow, quelle que soit la précision de ce dernier. Plus aucune commande ne passe, pytest compris. Pour « tout refuser sauf ce qui est nommé », on autorise ce qui est nommé et on choisit le mode dontAsk, comme ci-dessus.

Le bac à sable, la seule barrière qui arrête un script

Le bac à sable est posé par le système d’exploitation autour des commandes que lance Claude (Bash, PowerShell, et tous les programmes qu’elles démarrent, scripts Python compris). Il limite les fichiers lisibles et modifiables et les domaines joignables, quel que soit le texte de la commande.

  • Il fonctionne sous macOS, Linux et WSL2. Sous Windows natif, les commandes tournent sans bac à sable ; pour l’avoir sur un poste Windows, on lance Claude Code dans WSL2.
  • Par défaut, il laisse la lecture ouverte sur presque toute la machine : il faut lui dire quoi refuser.
  • Il ne couvre que les commandes. Les outils de fichiers de Claude (Read, Edit) suivent les règles de permissions. Les deux se complètent : un deny Read pour l’outil, un denyRead du bac à sable pour les scripts.
  • Ses chemins suivent la convention habituelle (/srv/production est absolu, ~/ part du dossier personnel), différente de celle des règles Read (// pour l’absolu).
{
  "permissions": {
    "deny": ["Read(//srv/production/**)"]
  },
  "sandbox": {
    "enabled": true,
    "allowUnsandboxedCommands": false,
    "filesystem": {
      "denyRead": ["/srv/production"]
    },
    "network": {
      "allowedDomains": ["pypi.org", "files.pythonhosted.org"]
    }
  }
}

Lecture en clair : ni l’outil de lecture de Claude ni aucune commande, script Python compris, ne lisent /srv/production ; côté réseau, les commandes joignent d’office l’index des paquets Python, et tout autre domaine demande votre accord en mode Manuel (en mode auto, il est refusé, sauf si le second modèle l’a approuvé pour cette commande) ; enfin allowUnsandboxedCommands: false empêche Claude de relancer hors du bac à sable une commande qui y a échoué. Même ainsi, tout ce que Claude lit dans le projet part chez le fournisseur : le bac à sable protège les fichiers qu’il exclut, pas ceux qu’on laisse lisibles.

Les réglages gérés, déployés par la DSI

Ce qui doit valoir pour tous les postes du cabinet, sans que personne puisse le retirer, va dans managed-settings.json, installé par la DSI aux emplacements du tableau des niveaux. Un deny posé là bloque partout ; certains réglages n’existent qu’à ce niveau, comme allowManagedPermissionRulesOnly, qui ne laisse s’appliquer que les règles du niveau géré.

{
  "permissions": {
    "disableBypassPermissionsMode": "disable",
    "deny": [
      "Bash(curl *)",
      "Bash(wget *)",
      "PowerShell(Invoke-WebRequest *)"
    ]
  }
}

Sur un parc macOS, Linux ou WSL2, la DSI y ajoute le bac à sable avec "failIfUnavailable": true, qui empêche Claude Code de démarrer si le bac à sable ne peut pas tourner. Sur un parc Windows natif, ce réglage empêcherait Claude Code de démarrer : la protection des données y repose entièrement sur leur absence du poste de travail. Si la politique du cabinet veut qu’un humain valide chaque commande, la DSI coupe aussi le mode auto ("disableAutoMode": "disable").

Un hook : ce qui doit arriver à chaque fois

Une consigne du CLAUDE.md, « lance les tests après chaque modification », peut être oubliée. Un hook ne l’est pas : c’est une commande que Claude Code lance lui-même à un moment précis, quoi que décide le modèle. Les moments les plus utiles : SessionStart (début ou reprise de session), PreToolUse (avant une action, qu’il peut bloquer), PostToolUse (après une action réussie), Stop (quand Claude a fini de répondre).

{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          { "type": "command", "command": "python -m pytest -q" }
        ]
      }
    ]
  }
}

Après chaque fichier créé ou modifié par Claude, les tests tournent. S’ils échouent, la commande se termine en erreur et un avertissement apparaît dans la session. Gardez des tests rapides : ils tournent à chaque modification. Un hook PreToolUse qui se termine avec le code 2 bloque l’action, même dans le mode le plus permissif ; un hook peut durcir les règles, jamais les assouplir. La commande /hooks liste les hooks actifs.

Un hook s’exécute avec vos droits, hors du bac à sable. Un dépôt cloné peut en contenir dans son .claude/settings.json : on les lit avant de travailler dans ce dépôt.

Devant une demande d’autorisation inconnue

Quand Claude demande l’accord pour une commande que vous ne connaissez pas :

  1. Demandez ce qu’elle fait. « Reformule en français ce que tu cherches à exécuter, et pourquoi. »
  2. Décidez en connaissance de cause. Utile et anodine : acceptez, ou ajoutez une règle dans .claude/settings.local.json (pour vous) ou .claude/settings.json (pour l’équipe, après en avoir parlé). Suspecte : refusez, et demandez une autre voie.

« Oui, et ne plus demander » enregistre une règle : relisez-la dans /permissions. On n’accepte jamais une demande sans l’avoir lue.
