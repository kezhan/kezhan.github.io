Annexe A. Glossaire Claude Code et IA générative

Définitions courtes des termes que rencontre un actuaire qui démarre avec Claude Code et l’IA générative, classées par thème. Ce qui touche à Claude Code décrit l’état au 29 septembre 2026, d’après la documentation officielle (code.claude.com/docs) : l’outil change vite, et c’est cette documentation qui fait foi.

Termes Claude Code

Agent. Programme qui interroge un modèle de langue, lit vos fichiers, exécute du code, lit les sorties et recommence jusqu’à atteindre le but fixé. C’est le niveau 2 du cadrage (chapitre « Pas toujours besoin d’un modèle de langue », partie 1). Claude Code, Cursor et Cline sont des agents.

Allow, ask, deny. Les trois listes de règles de permissions d’un fichier settings.json. allow : ce que Claude fait sans demander. ask : ce pour quoi il demande toujours, par exemple git push. deny : ce qu’il ne fait pas. Claude Code examine les règles dans l’ordre deny, puis ask, puis allow, et la première qui correspond décide : un deny l’emporte toujours, à quelque niveau de réglages qu’il soit écrit. Un deny ne vise que la forme d’action qu’il décrit : un deny Read sur un dossier n’empêche pas un script Python autorisé d’ouvrir les fichiers de ce dossier. Voir l’annexe D.

Auto memory (mémoire automatique). Notes que Claude écrit lui-même au fil des sessions (commandes utiles, préférences, corrections reçues), dans ~/.claude/projects/<projet>/memory/. Le fichier d’index MEMORY.md est chargé au début de chaque session (ses 200 premières lignes, ou 25 Ko). Active par défaut, elle est stockée sur votre machine, hors du dépôt : elle ne se partage pas avec l’équipe. Elle complète le CLAUDE.md que vous écrivez vous-même.

Bac à sable (sandbox). Barrière posée par le système d’exploitation autour des commandes que lance Claude (Bash, PowerShell, et les programmes qu’elles démarrent) : elle limite les fichiers lisibles et modifiables et les domaines joignables. C’est la seule protection qui arrête aussi un script Python. Elle fonctionne sous macOS, Linux et WSL2, pas sous Windows natif. Par défaut, la lecture reste ouverte sur toute la machine : il faut la configurer (réglage sandbox, annexe D).

Bash literacy. Savoir lire ce que Claude exécute dans le terminal sans savoir l’écrire soi-même : reconnaître ls, cd, cat, python, git, et leurs équivalents PowerShell sous Windows. Voir l’annexe Installation.

Checkpoint et /rewind. Claude Code enregistre l’état des fichiers avant chaque prompt ; /rewind, ou Échap deux fois, revient à un point antérieur. Les modifications faites par une commande (un script qui écrit un fichier, une suppression) ne sont pas suivies : Git reste le vrai point de retour.

CLAUDE.md. Fichier Markdown d’instructions lu au démarrage de chaque session : conventions du projet, fichiers de référence, erreurs à ne pas refaire. Il existe à plusieurs niveaux : projet (./CLAUDE.md ou ./.claude/CLAUDE.md, versionné, partagé avec l’équipe), local (./CLAUDE.local.md, pour vous seul, à exclure de Git), utilisateur (~/.claude/CLAUDE.md, valable pour tous vos projets), organisation (déployé par la DSI). La documentation conseille de rester sous 200 lignes par fichier. Ce sont des consignes, pas des verrous : pour qu’une action ait lieu à coup sûr, on écrit un hook. Modèle en annexe C.

CLI (interface en ligne de commande). Claude Code lancé par la commande claude dans un terminal. La surface la plus directe pour les usages scriptés.

Commandes et skills. Les commandes personnalisées (/nom) ont été fusionnées dans les skills. Un skill est un dossier .claude/skills/<nom>/ qui contient un fichier SKILL.md ; Claude le charge quand la tâche s’y prête, ou quand vous l’appelez par /nom. L’ancien dossier .claude/commands/ fonctionne toujours. Versionnés dans le dépôt, les skills se partagent avec l’équipe.

Commit (Git). Enregistrer une version des fichiers dans l’historique du dépôt. Un fichier non commité reste sur le disque, mais il n’a pas de point de retour. Un commit non poussé (git push) n’existe que sur votre poste. Voir l’annexe E.

Diff. Affichage de ce qui change entre deux versions d’un fichier. L’extension VS Code le montre côte à côte avant d’appliquer une modification.

Explorer, planifier, coder, commiter. Le déroulé recommandé par Anthropic : Claude lit le code et les références, propose un plan que vous validez, écrit, puis la version validée est figée dans Git. Le mode plan (indicateur de mode dans VS Code, Shift+Tab dans le terminal) fait la première moitié sans rien modifier.

Fenêtre de contexte. Quantité de texte, mesurée en tokens, que le modèle prend en compte à un instant donné : la conversation, les fichiers lus, les sorties des commandes, le CLAUDE.md. Sa taille dépend du modèle. Quand elle se remplit, Claude Code résume la conversation (la compaction), et des détails se perdent.

Hallucination. Réponse affirmée avec assurance mais fausse : un chiffre, une référence, un numéro d’article. Elle vient du mécanisme même du modèle, qui produit du plausible. La parade : un chiffre vient d’un code exécuté, une référence se vérifie dans le texte source. Voir le chapitre « Un modèle qui écrit le mot suivant » (partie 1).

Harnais (harness). Le programme qui fait travailler le modèle : Claude Code lui-même, ses outils, ses consignes, sa gestion du contexte. Il peut se dérégler sans que le modèle change. Le post-mortem d’Anthropic du 23 avril 2026 (anthropic.com/engineering/april-23-postmortem) décrit trois changements de Claude Code (effort de raisonnement abaissé, bug de cache, consigne de concision), entre le 4 mars et le 20 avril 2026, qui ont dégradé les réponses alors que l’API n’était pas touchée.

Hook. Commande que Claude Code lance lui-même à un moment précis de la session, quoi que décide le modèle. Les événements les plus utiles : SessionStart (début ou reprise de session), PreToolUse (avant une action, qu’il peut bloquer), PostToolUse (après une action réussie), Stop (quand Claude a fini de répondre). Il se déclare dans un settings.json. À ne pas confondre avec un hook Git (après un commit, avant un push), qui appartient à Git et pas à Claude Code. Exemple en annexe D.

Import @. Dans un CLAUDE.md, @chemin/fichier insère le contenu de ce fichier, et il est chargé à chaque session. À réserver aux fichiers courts ; pour un document long, on cite son chemin sans @, et Claude l’ouvre quand il en a besoin. Dans un prompt, @fichier désigne simplement un fichier à lire pour cette demande.

MCP (Model Context Protocol). Standard ouvert pour brancher Claude Code sur des outils externes : une base de données, GitHub, un outil interne. Ce qu’un serveur MCP renvoie entre dans la conversation, donc part chez le fournisseur du modèle.

Mémoire de projet. Tout ce que Claude relit à chaque session : CLAUDE.md, règles de .claude/rules/, fichiers importés par @, auto memory. Ce qui se partage avec l’équipe passe par le dépôt : CLAUDE.md, .claude/rules/, skills. Ce qui reste à vous : CLAUDE.local.md, ~/.claude/CLAUDE.md, l’auto memory. Un dossier .claude/memory/ n’est pas un mécanisme de Claude Code : rien ne le charge de lui-même. Le réglage autoMemoryDirectory change l’emplacement de l’auto memory, sans en faire une mémoire d’équipe.

Modes de permission. Ce que Claude fait sans vous demander. default (Manuel) : il lit dans le projet et demande avant de modifier un fichier ou de lancer une commande. acceptEdits : il accepte les modifications de fichiers. plan : il lit et propose, ne modifie rien. auto : un second modèle examine chaque action, laisse passer ce qu’il juge sans risque et bloque le reste. S’y ajoutent dontAsk et bypassPermissions. Depuis la version 2.1.283, auto est le mode de départ par défaut dans le terminal et dans VS Code. En cours de session, on change de mode par l’indicateur de mode sous la zone de saisie dans VS Code, par Shift+Tab dans le terminal.

Niveaux de réglages. Les fichiers settings.json existent à quatre niveaux, du plus fort au plus faible : géré par la DSI (managed-settings.json, que ni l’utilisateur ni le projet ne peuvent contourner), local (.claude/settings.local.json, ce projet sur votre seul poste, hors Git), projet (.claude/settings.json, versionné), utilisateur (~/.claude/settings.json, tous vos projets). Il n’existe pas de settings.cabinet.json : une politique commune à tout un cabinet se déploie par les réglages gérés.

Outil (tool). Une capacité que Claude peut utiliser : lire un fichier (Read), le modifier (Edit), exécuter une commande (Bash, ou PowerShell sous Windows), lire une page web (WebFetch). Chaque appel d’outil passe par les permissions et s’affiche dans la session.

Permissions. Les règles qui disent ce que Claude fait sans demander, avec demande, ou jamais. Elles évitent la fatigue de validation et les accidents ; elles ne protègent pas des données. Voir l’annexe D.

Prompt. Le texte que vous envoyez au modèle. Dans Claude Code, votre message dans la zone de saisie.

Prompting d’intention. Décrire le quoi (le résultat métier attendu) plutôt que le comment (le code à écrire). Voir le chapitre « Piloter l’IA » (partie 1).

Règles (.claude/rules/). Fichiers d’instructions rangés par thème dans le dossier .claude/rules/ du projet. Un en-tête paths: limite une règle à certains fichiers, par exemple les scripts de provisionnement ; sans cet en-tête, la règle est chargée à chaque session.

Settings.json. Fichier de configuration de Claude Code : permissions, hooks, bac à sable, mode de départ. Voir « Niveaux de réglages » et l’annexe D.

Sous-agent. Une tâche déléguée à une instance de Claude qui a son propre contexte et ses propres consignes, par exemple un sous-agent relecteur-solvabilite2. Un sous-agent trouvé sur internet est un fichier d’instructions qui travaille avec vos permissions : on le lit avant de l’installer.

Token. Unité de texte que manipule le modèle : un mot courant, un fragment de mot rare, un signe de ponctuation. Le modèle lit et écrit des tokens, et l’API se facture au token, en entrée et en sortie.

Termes IA générative au sens large

API (interface de programmation). Interface pour appeler un modèle depuis un programme. Le SDK d’Anthropic, en Python, s’en sert. Facturation au token.

Attention. Mécanisme central des transformers : pour produire chaque token, le modèle pondère l’influence de tous les tokens qui précèdent.

Complaisance (sycophancy), ou biais de confirmation. Tendance du modèle à abonder dans votre sens, à valider une hypothèse parce que vous l’avez avancée. La parade : demander explicitement la critique, avant chaque décision qui compte. Voir le chapitre « Piloter l’IA » (partie 1).

Cross-entropie. Fonction de perte utilisée pour entraîner les LLM. Analogue actuariel : la déviance d’un GLM.

Descente de gradient. Méthode d’optimisation qui ajuste les paramètres d’un modèle pas à pas. Utilisée pour entraîner les LLM ; familière à qui a pratiqué le gradient boosting.

Embedding (plongement). Représentation d’un texte par un vecteur de nombres, qui sert à la recherche par le sens. Peu utile à l’actuaire qui se sert de Claude Code.

Facturation au token. Tarification de l’API au nombre de tokens envoyés et reçus. Elle permet de suivre le coût appel par appel.

Fine-tuning (ajustement fin). Entraînement complémentaire d’un modèle déjà entraîné, sur un corpus spécialisé. Hors du périmètre de cette formation.

LLM (grand modèle de langue). Modèle entraîné sur un très grand corpus de texte à prédire le token suivant. Claude, ChatGPT, Gemini et Mistral en sont. Voir le chapitre « Un modèle qui écrit le mot suivant » (partie 1).

Modèle. Une version précise d’un LLM, désignée par un identifiant : claude-opus-5-5, claude-sonnet-5-5, claude-haiku-4-5. Au 29 septembre 2026, Opus 5.5 est le modèle par défaut de Claude Code. À distinguer du harnais qui le fait travailler.

Prompt caching (mise en cache du prompt). Fonction de l’API qui réutilise à moindre coût un début de prompt identique d’un appel à l’autre, utile quand un programme appelle le modèle de nombreuses fois avec le même préambule.

Prompt engineering. L’art de formuler les prompts. La formation parle plutôt de prompting d’intention.

Quarto. Outil de publication scientifique (pages web, PDF, diapositives, livres) qui exécute le code contenu dans les documents et en insère les sorties. C’est le successeur de R Markdown. Les fiches de la bibliothèque sont des fichiers Quarto (.qmd).

RAG (génération augmentée par récupération). Le modèle répond en s’appuyant sur des documents retrouvés à la volée dans un corpus (recherche, base documentaire). Utile pour interroger la documentation propre au cabinet.

RLHF (apprentissage par renforcement à partir de retours humains). Méthode d’alignement : le modèle est ajusté pour produire les réponses que des évaluateurs humains préfèrent. C’est une des sources connues de la complaisance, car une réponse qui va dans le sens de l’utilisateur est souvent mieux notée.

Sortie structurée (structured output). Réponse de l’API au format JSON, conforme à un schéma fourni. Utile quand un programme lit la réponse (niveau 3 du cadrage).

Température. Paramètre de l’API qui règle la part d’aléa dans le choix des tokens : basse, des réponses plus constantes ; haute, plus variées. Même basse, deux appels ne garantissent pas la même réponse : un chiffre se reproduit par un code, pas par un prompt.

Tokenisation. Découpage du texte en tokens, première étape du traitement par le modèle.

Transformer. Architecture de réseau de neurones sur laquelle reposent les LLM actuels, introduite par une équipe de Google en 2017.

Termes de tarification

Bonus-malus (coefficient de réduction-majoration, CRM). Coefficient de l’assurance automobile française, de 0,50 (bonus maximal) à 3,50 (malus maximal), souvent noté de 50 à 350. La fréquence de sinistres croît avec lui.

Discrétisation. Découpage d’une variable continue en tranches justifiables pour le métier, par exemple l’âge en 18-25, 26-35, et ainsi de suite. Voir les fiches P1 et P2.

Exposition (exposure). Durée d’observation d’une police, en années. Une fréquence se calcule comme un rapport de sommes, somme des sinistres sur somme des expositions, et pas comme la moyenne des rapports ligne à ligne.

Fréquence × coût moyen. Décomposition de la prime pure. Deux GLM séparés (Poisson pour la fréquence, Gamma pour le coût) ou un seul GLM Tweedie ; les deux approches supposent l’indépendance entre le nombre et le montant des sinistres.

GLM (modèle linéaire généralisé). La famille de modèles de référence pour la tarification. Voir le chapitre « Modéliser : choisir, calibrer, valider » (partie 2) et les fiches P2 à P5.

Offset (en GLM). Terme fixe ajouté au prédicteur linéaire, sans coefficient à estimer. En fréquence Poisson, la cible est le nombre de sinistres et l’offset vaut \(\ln(\text{exposition})\). L’erreur à éviter : passer l’exposition en weights en gardant le nombre de sinistres comme cible.

Prime pure. Espérance du coût des sinistres d’une police, avant chargements (frais, marge, taxes).

Rapport sinistres à primes (S/P, loss ratio). Charge de sinistres rapportée aux primes acquises (\(\text{prime annuelle} \times \text{exposition}\)), pas aux primes émises.

Tweedie. Famille de lois indexée par la puissance \(p\) de la variance. Pour \(1 < p < 2\), c’est une loi de Poisson composée de lois Gamma : une masse en zéro (pas de sinistre) et des montants positifs. Elle modélise la prime pure en un seul GLM, et suppose elle aussi l’indépendance entre nombre et montant des sinistres. Voir la fiche P4.

Termes de provisionnement, de vie et de Solvabilité II

Best estimate. Meilleure estimation des engagements au sens de Solvabilité II, sur des hypothèses réalistes propres à l’organisme. La prudence (tables réglementaires, taux technique plafonné) relève des provisions des normes françaises, pas du best estimate.

Bootstrap. Rééchantillonnage qui estime par simulation la distribution d’une statistique. En provisionnement, le bootstrap ODP d’England et Verrall donne une distribution des réserves à l’ultime ; sur le triangle de Taylor-Ashe, son écart-type est d’environ 3,0 millions. Voir la fiche R4.

Chain-Ladder. Méthode déterministe de provisionnement non-vie : on projette le triangle à l’aide de facteurs de développement. Sur le triangle de Taylor-Ashe (unités non monétaires), la réserve totale vaut 18 680 856 et l’ultime total 53 038 946 : les deux se confondent facilement. Voir la fiche R1.

Facteur de développement. Rapport entre les montants cumulés de deux années de développement successives, estimé sur la partie connue du triangle. On dit aussi facteur age-to-age.

Graine (seed). Valeur initiale d’un générateur aléatoire : rng = np.random.default_rng(seed=42). Pour que la modification d’un calcul ne change pas les tirages des autres, on donne un générateur à chaque composant : np.random.SeedSequence(42).spawn(k).

Mack. Modèle stochastique sous-jacent au Chain-Ladder (Mack 1993). Il donne l’erreur quadratique moyenne de prédiction (MSEP) des réserves, par année d’origine et au total. Sur Taylor-Ashe, la racine de la MSEP de la réserve totale vaut 2 447 095, soit un coefficient de variation de 13,1 %. Voir la fiche R3.

Marge de risque. Composante des provisions techniques de Solvabilité II, calculée par le coût du capital (articles 37 à 39 du Règlement délégué 2015/35). Ce n’est pas un quantile d’une distribution de réserves. Son homologue en IFRS 17 est l’ajustement pour risque non financier.

Monte Carlo. Méthode de calcul par tirages aléatoires répétés. Voir la fiche I2.

\(q_x\) et \(\mu_x\). \(q_x\) : probabilité qu’une personne d’âge \(x\) exact décède avant l’âge \(x + 1\). \(\mu_x\) : force de mortalité, le taux instantané à l’âge \(x\). Les lois de Gompertz et de Makeham portent sur \(\mu_x\). Le modèle de Lee-Carter porte sur le logarithme des taux centraux de mortalité \(m_x\). Voir les fiches V1 et V2.

Reproductibilité. Relancer un calcul et retrouver la même sortie. Il faut une graine fixée, mais aussi les mêmes données et le même environnement : NumPy ne garantit pas que le flux d’un Generator reste identique d’une version à l’autre. C’est ce qui rend un calcul vérifiable par un tiers (fonction actuarielle, audit interne, contrôleur). Voir le chapitre « Versionner les résultats » (partie 3).

Responsable de la fonction actuarielle. La personne qui porte la fonction actuarielle exigée par Solvabilité II, et le terme à employer pour la désigner.

Risque de réserve. Dans Solvabilité II, il se mesure à horizon d’un an (approche de Merz et Wüthrich pour un modèle stochastique), et pas comme un quantile d’une distribution des réserves à l’ultime.

Triangle de liquidation. Tableau croisé année d’origine × année de développement des paiements cumulés, ou des charges, de sinistres. C’est l’entrée des méthodes de provisionnement.

TipExercice : trouvez les erreurs

Un collègue a pris ces notes pendant une démonstration. Lesquelles sont fausses, et que faut-il écrire à la place ?

  1. « \(q_x\) est le taux de mortalité instantané à l’âge \(x\). »
  2. « Pour imposer la même politique à toutes les équipes, on crée un settings.cabinet.json que chaque projet inclut. »
  3. « Avec Read(./data/assures/**) en deny, Claude ne peut plus lire ces fichiers, quoi qu’il arrive. »
  4. « Sur Taylor-Ashe, le Chain-Ladder donne un ultime total de 18 680 856. »
  5. « Le dossier .claude/memory/, versionné, est la mémoire d’équipe de Claude Code. »
Voir la réponse

Les cinq sont fausses.

  1. \(q_x\) est une probabilité : celle de décéder entre \(x\) et \(x + 1\). Le taux instantané est la force de mortalité \(\mu_x\).
  2. Ce fichier n’existe pas, pas plus qu’une directive d’inclusion entre fichiers de réglages. Une politique commune se déploie par les réglages gérés (managed-settings.json), que la DSI installe sur les postes et que personne ne peut contourner.
  3. Le deny couvre l’outil de lecture de Claude Code et les commandes qu’il reconnaît (cat, head, tail…). Un script Python autorisé ouvre le fichier lui-même, et ce que Claude en affiche part chez le fournisseur. Seul le bac à sable arrête un script, et il n’existe pas sous Windows natif : les données d’assurés n’ont rien à faire dans le dossier de travail.
  4. 18 680 856 est la réserve totale. L’ultime total vaut 53 038 946.
  5. Ce dossier n’est pas un mécanisme natif : rien ne le charge. L’équipe partage ses consignes par le CLAUDE.md du projet, les règles de .claude/rules/ et les skills, tous versionnés. L’auto memory, elle, reste sur chaque poste.
