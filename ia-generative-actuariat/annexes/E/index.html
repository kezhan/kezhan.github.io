Annexe E. Conventions Git légères pour une équipe actuarielle

Git a été pensé pour des équipes de développement logiciel nombreuses. Pour une équipe actuarielle de quelques personnes, la plupart de leurs conventions sont surdimensionnées. Cette annexe propose un déroulé léger mais discipliné, calibré pour un cabinet, qui assure la traçabilité, le partage et le retour en arrière sans rituel inutile.

Ce qu’il faut garder en tête avant tout le reste :

  • Un fichier non commité reste sur le disque, mais il n’a pas de point de retour : la prochaine modification l’écrase sans recours.
  • Un commit non poussé n’existe que sur votre poste : invisible pour les collègues, perdu avec le poste.
  • Un tag ne fige que ce qui est versionné : ni les données exclues par le .gitignore, ni l’environnement (versions de Python et des bibliothèques). Et git push n’envoie pas les tags.

Le déroulé recommandé en cinq règles

Règle 1. Une branche par projet, pas par fonctionnalité. Le Git Flow classique (branches de fonctionnalité, develop, release, master) est trop lourd pour une équipe actuarielle. Pour la plupart des projets d’un cabinet, la seule branche main suffit. Pour un chantier long (la refonte d’un module de provisionnement), une branche refonte-provisionnement en parallèle, fusionnée régulièrement dans main.

Règle 2. Un commit à chaque étape validée. Une étape validée, c’est une modification qui marche. Le calcul des facteurs de développement tourne et ses tests passent : commit. Le bootstrap tourne : commit. Pas dix changements dans un commit, pas un commit pour ouvrir une parenthèse et un autre pour la fermer.

Règle 3. Des messages qui disent l’intention. « Ajoute le bootstrap ODP des réserves » est un bon message. « Modif chain_ladder.py + nouveau fichier bootstrap.py + tests » est un mauvais message : il dit ce qui a bougé, pas pourquoi.

Règle 4. Pousser chaque jour. À la fin de chaque journée de travail : git push. Ce qui n’est pas poussé n’existe que sur votre poste.

Règle 5. Un tag par livraison réglementaire, après relecture. Quand une version part au contrôleur ou au comité, un second actuaire la relit, puis on l’étiquette et on pousse l’étiquette :

git tag -a v2026-q1-scr -m "SCR Solvabilité II, T1 2026, remis le 2026-04-15"
git push origin v2026-q1-scr

Les commandes à connaître

Pour travailler seul :

Commande À quoi elle sert Quand l’utiliser
git status Qu’est-ce qui a changé ? Avant chaque commit, et dès qu’on s’y perd
git diff Le détail exact des changements Avant un git add, pour voir ce qu’on va figer
git add <fichier> Choisir ce qu’on fige Une fois le diff relu
git commit -m "..." Figer cette version Après chaque étape validée
git log --oneline L’historique, une ligne par commit Pour retrouver une version passée

Pour travailler à plusieurs, s’y ajoutent :

Commande À quoi elle sert
git pull Récupérer le travail des collègues
git push Envoyer ses commits sur le serveur partagé
git push origin <tag> Envoyer une étiquette, que git push seul n’envoie pas
git switch <branche> Passer sur une autre branche

Les commandes plus avancées (rebase, cherry-pick, bisect) servent rarement dans un projet actuariel. Le jour où l’une d’elles est utile, Claude sait la proposer et vous l’expliquer avant de la lancer.

Le pattern « Claude, commite-le »

Avec Claude Code, le commit fait partie du dialogue. À chaque étape validée :

“Cette version me convient, commite-la avec un message qui décrit l’intention.”

Claude lance git add puis git commit et montre le résultat. Vous relisez le message proposé et le corrigez s’il est trop technique. Le modèle de réglages de l’annexe D autorise git add et git commit sans demander, et fait toujours demander avant un git push : le commit devient un réflexe, l’envoi reste une décision.

Format des messages de commit

Le plus souvent, un titre et deux ou trois lignes suffisent.

Ajoute le bootstrap ODP des réserves

Distribution de la réserve totale par 10 000 simulations, graine 42.
Réserves simulées sauvegardées en parquet pour la piste d'audit.

Première ligne : l’intention de la modification, à la voix active, sans point final, en une soixantaine de caractères au plus. Une ligne vide. Puis quelques lignes de contexte : pourquoi, et ce qui mérite d’être noté.

Pour une modification triviale (une coquille, une mise à jour de dépendance), une seule ligne suffit.

Corrige l'inversion d'indices dans facteurs_developpement

À proscrire :

  • « fix », « update », « wip » sans contexte : illisible six mois plus tard.
  • « Add 47 lines to chain_ladder.py » : dit le quoi technique, pas le pourquoi métier.
  • « voir Jira ACT-1245 » seul : la trace ne tient que tant que l’outil de tickets existe et reste accessible.

Branches et relecture

Pour un projet courant, une seule branche main. On se relit en regardant les commits du collègue (git log -p, ou l’historique dans VS Code).

Pour un calcul réglementaire, le principe des quatre yeux : un second actuaire relit avant la livraison. Deux façons légères de le tenir :

  • une demande de fusion (pull request) sur le serveur Git, que le relecteur approuve avant que la modification entre dans main ;
  • la relecture du diff entre la dernière version livrée et la nouvelle, avant de poser l’étiquette : git diff v2025-q4-scr..HEAD.

Pour un chantier long, une branche dédiée :

main (ligne de référence, étiquetée à chaque livraison)
 \
  refonte-provisionnement (en parallèle, quelques semaines)
     \
      [fusion régulière dans main, après relecture]

Pour un projet partagé entre plusieurs équipes, le pattern classique : main et une branche par demande de fusion, fusionnée après relecture. On sort alors du cadre de cette annexe.

Étiquettes par version réglementaire

Pour les calculs réglementaires (SCR, provisions IFRS 17, ORSA), une étiquette à chaque livraison officielle. Format conseillé : v<année>-<période>-<calcul>.

v2026-q1-scr           SCR Solvabilité II, premier trimestre 2026
v2026-h1-ifrs17        Provisions IFRS 17, premier semestre 2026
v2026-orsa             ORSA annuel
v2026-q1-pricing-auto  Tarif auto, premier trimestre 2026

Ce que l’étiquette fige, et ce qu’elle ne fige pas. Elle désigne un commit : le code, les paramètres et la documentation versionnés tels qu’ils étaient à la livraison. Elle ne fige pas les données d’entrée, exclues par le .gitignore, ni l’environnement : une autre version de Python ou de NumPy peut changer un résultat, et NumPy ne garantit pas que le flux d’un Generator reste identique d’une version à l’autre. Pour qu’un tiers puisse refaire le calcul trois ans plus tard, il faut donc aussi :

  1. Archiver les données d’entrée hors de Git, sur le stockage du cabinet, et noter dans un fichier versionné leur emplacement et leur empreinte (un hachage SHA-256, qui prouve que le fichier n’a pas changé).
  2. Figer l’environnement : la liste exacte des versions (pip freeze > requirements.lock, ou le fichier de verrouillage de votre gestionnaire de paquets), commitée avec le code.
  3. Pousser l’étiquette : git push origin v2026-q1-scr, ou git push --follow-tags, qui envoie avec les commits les étiquettes annotées qui les accompagnent.

Modèle à copier dans tout nouveau projet.

À adapter à votre arborescence. Le principe : ce qui est généré (caches, artefacts lourds) ou personnel (réglages locaux, secrets) reste hors du dépôt. Les données nominatives, elles, n’ont rien à faire dans le dossier de travail, .gitignore ou pas : Claude lit ce qui s’y trouve, et ce qu’il lit part chez le fournisseur.

Revenir en arrière

« J’ai fait une modification qui casse tout. » Si elle n’est pas commitée, git restore <fichier> remet la dernière version commitée ; c’est irréversible, les changements non commités de ce fichier sont perdus. Si la modification vient de Claude, /rewind (ou Échap deux fois) revient à l’état d’avant un prompt, pour ce que Claude a modifié avec ses outils de fichiers ; ce qu’une commande a modifié n’est pas suivi. Si c’est déjà commité : git log --oneline pour trouver le commit d’avant, puis git restore --source <hash> <fichier>.

« J’ai un conflit après un git pull. » Un collègue et vous avez modifié les mêmes lignes. git status liste les fichiers en conflit. Dans chacun, repérer les marqueurs <<<<<<<, garder la bonne version, retirer les marqueurs, puis git add <fichier> et git commit. En cas de doute : « explique-moi ce conflit et propose une résolution, sans rien modifier ».

« J’ai perdu un fichier. » S’il a été commité un jour, git log --oneline -- <fichier> trouve les commits qui l’ont touché, et git restore --source <hash> <fichier> le rétablit depuis l’un d’eux.

TipExercice : le calcul qui ne se reproduit pas

On vous demande de refaire le SCR livré sous l’étiquette v2026-q1-scr. Sur votre poste, git switch --detach v2026-q1-scr répond que l’étiquette n’existe pas. Une collègue la retrouve sur son poste ; vous relancez le calcul : le chiffre ne retombe pas exactement sur celui qui a été livré. Qu’est-ce qui a pu se passer, et que fallait-il faire au moment de la livraison ?

Voir la réponse
  1. L’étiquette n’a jamais été poussée. git push n’envoie pas les tags : elle n’existait que sur le poste de qui l’a posée. Il fallait git push origin v2026-q1-scr.
  2. Les données ont changé. Exclues par le .gitignore, elles ont été réextraites depuis. Il fallait les archiver et noter leur empreinte dans un fichier versionné.
  3. L’environnement a changé. D’autres versions de Python, de NumPy ou de statsmodels donnent d’autres résultats, et le flux d’un générateur aléatoire peut varier entre versions de NumPy. Il fallait commiter la liste exacte des versions.

Enfin, la relecture par un second actuaire avant le tag aurait été l’occasion de vérifier ces trois points.
